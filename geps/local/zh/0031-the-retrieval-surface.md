# GEP-0031: 检索面

## 摘要

智能体在编辑代码之前，必须先找到代码。本 GEP 利用工具链已有的信息，为 Gandora 提供了一个 AI 原生感知层：**代码地图**（`gan lsc map`）列出项目、标准库及每个已安装包，并附有源码路径与渲染后的头部；**文件名搜索**（`find`）与**内容搜索**（`grep`，正则或 BM25 排序）在包含项目源码、项目文档及每个包随附的 `.gan` 源码（GEP-0006）的语料库上进行检索；**区间读取**（`read`）获取单个代码块：按名称获取某个函数，或按路径加行范围获取某段代码，而不是读取整个文件。每项能力都对应一次 `gan lsc` 查询并返回一个 JSON 值；`gan-mcp` 将全部四项作为工具转发，因此 shell 与 MCP 客户端会看到相同的答案。

## 动机

通用检索栈通常会求助于 tree-sitter 和索引器；Gandora 两者都不需要。编译器本身就是解析器（`symbols`、`wsymbols`、`definition` 已经返回名称、头部、行号和路径），而 GEP-0006 已经让每个发布的包都携带其 `.gan` 源码，供宏消费者使用——这意味着标准库和第三方依赖*天然可进行源码搜索*，双语的 `@doc` 说明文字也包含在内。缺失的是表层：一张智能体用来了解万物位置的地图，以及三个动词——find、grep、read——其精确度足以让它永远不必将整个文件分页载入上下文。

文档是有意作为语料库的一部分，而非事后补充：项目的 `docs/**/*.md` 和 README 能回答符号表无法回答的“我该如何使用它”这类问题；而 `@doc`/`@moduledoc` 说明文字随发布的 `.gan` 源码一同传播，因此一次 grep 就能在同一遍扫描中同时覆盖代码及其文档。

## 范围

`gan-lsc` 中的 `map`、`find`、`grep` 和 `read` 查询；语料库定义；可选的 `fd`/`rg` 加速以及必需的回退机制；`gan-mcp` 中的四个转发工具。持久化索引、嵌入和跨项目搜索不在范围内。

## 术语

- **Corpus（语料库）**：检索操作所基于的文件集合（R002）。
- **依赖源**：已安装包在其 `_gan/` 目录下随附的 `.gan` 文件，通过 `gandora.toml` 标记枚举。
- **块**：一个定义及其上方的注释行。

## 规范

**GEP-0031-R001：** 检索表面是四个 `gan-lsc` 查询——`map`、`find`、`grep`、`read`——各自在 stdout 上返回一个 JSON 值（GEP-0015-R001A）。`gan-mcp` 必须（MUST）将其转发为工具 `gan_map`、`gan_search_files`、`gan_search_content` 和 `gan_read`，且不咨询任何模型（GEP-0028）。两个表面对于同一问题返回相同的值。

**GEP-0031-R002：** 语料库依次为：项目的 Gandora 源码（配置的源码根目录加上顶层 `tests/`）；项目的文档（根目录及 `docs/` 下的 `README*` 和 `*.md`，递归）；以及——在 `find`/`grep` 的 `--deps` 标志之后——每个已安装包的 `.gan` 源码，通过项目 `.venv` 下的 `gandora.toml` 标记发现（GEP-0006）。构建输出、缓存以及除依赖源码之外的 `.venv` 内部内容永远不在语料库中。

**GEP-0031-R003：** `map` 返回图谱（atlas）：对于项目，每个模块及其路径和渲染后的公共头部；对于标准库和每个已安装包，每个模块及其随附 `.gan` 源码的路径以及相同的渲染后的头部。头部是一行定位说明——签名加上该定义的 `@doc` 第一句（`def map(xs, f) — 将 \`f\` 应用于每个元素。`）——因此该图谱一次拉取即可回答“这里有什么以及它做什么”。图谱还列出文档文件。所有内容均已排序；项目内的路径为项目相对路径，依赖路径为绝对路径。`map <Mod>` 将图谱缩小到名称包含 `<Mod>` 的模块。

**GEP-0031-R003A：** `map --query <words>` 搜索图谱本身：每个公共定义——无论是项目的还是已安装的——都是一个 BM25 文档（模块名、函数名、头部和 `@doc` 第一句；常量与 R005 相同），答案是排序后的符号，每个符号携带 `target`、`head`、`path` 和 `score`。这就是轻量级英语 `@doc` 渠道（GEP-0007-R011）带来的价值：单句文档是语义键，因此“读取返回判定结果的文件”可以找到 `File.read`，而无须知道其名称。上限为 20 个符号，并报告 `truncated`。

**GEP-0031-R004：** `find <pattern>` 匹配语料库中的文件*名称*（子字符串或当模式包含 `*`/`?` 时使用通配符）。当 `fd` 在 `PATH` 上时，它可（MAY）加速项目遍历；纯回退必须（MUST）返回相同的集合。输出是排序后的路径列表。

**GEP-0031-R005：** `grep <pattern>` 搜索文件*内容*。默认模式是正则表达式，当存在 `rg` 时由其加速，并提供形状相同的纯回退：一个按路径顺序排列的 `{path, line, text}` 匹配列表。`grep --ranked <words>` 是用于散文的查询模式：文件使用 BM25 评分（k1 = 1.2，b = 0.75，整个文件作为文档，`[a-z0-9_]+` 分词，小写化），答案是排名靠前的文件，每个文件附带其最佳匹配行。两种模式都限制其输出（200 个匹配；10 个排名文件）且必须（MUST）通过 `truncated` 标志说明这一点——静默截断会被视为完整性。

**GEP-0031-R006：** `read` 只获取以下之一：`read <path> <from> <to>`——语料库文件的从 1 开始且包含的行范围；`read <Mod>`——某个模块（项目或已安装）的完整源码；`read <Mod.fun>`——某个定义的代码块：其注解（`@doc`/`@param`/`@spec`/`@example`/自定义属性以及紧邻上方的注释）直到其最后一个子句，通过编译器自身的 `definition`/`symbols` 行数据定位，并以下一个符号为边界。答案携带 `{path, from, to, text}`，以便代理可以引用并编辑其所读取的内容。

**GEP-0031-R007：** 确定性与封闭性：结果有序或按分数排序，并具有文档化的平局打破规则（路径顺序），绝不依赖墙钟时间或环境；外部二进制文件只是一种优化，而非要求；查询只读取文件和标记——不写入、不联网、不涉及模型。

## 理由

一个实现，两个界面：查询位于 `gan-lsc`，因为语言智能已经在那里以 JSON 形式应答；`gan-mcp` 则转发而非重新实现，正如 doc 和 pack 工具所做的那样（GEP-0026/0028）。BM25 采用真正的公式，而不是用“相关性”来含糊其辞，因为代理在调优自己的查询时需要排序是可预测的；选择整文件作为文档使得在没有索引的情况下计算依然可靠。`read` 之所以存在，是因为代理检索代价高昂的失败模式是：为了使用一个 600 行文件中的六行而分页读取它——而编译器知道这六行在哪里。

## 向后兼容性

纯增量式：四个新查询，四个新工具。

## 安全性与确定性

检索读取项目、其文档以及已安装的标记/源——
与编译器在构建时已读取的是同一信任域。
`fd`/`rg` 以固定的参数列表运行；它们的缺失会改变
性能，而非结果（R004/R005/R007）。

## 工具与 AI 使用

预期循环为：先执行一次 `gan_map` 来定位方向；再用 `gan_search_files` / `gan_search_content` 查找位置；然后用 `gan_read` 精确读取需要修改的代码块；最后进入编写→`gan build`→`gan test` 循环（GEP-0026）。简报和资源包保持提示词大小；地图则是代理按需拉取的更大图集。

## 被拒绝的替代方案

### Tree-sitter 文法和外部索引器

第二个解析器会偏离真正的解析器，而索引是带有失效问题的缓存。编译器已经解析了代码库中的所有内容，并且包源代码在 GEP-0006 中就已经存在于磁盘上——遍历它们的速度在项目规模下已经足够快。

### 编译产物搜索

搜索生成的 Python 代码只会找到修饰过的名称，并会遗漏宏和文档。对于人类和代理而言，`.gan` 源文件都是权威记录产物；编译输出则是给解释器用的。

## 一致性

测试 MUST 覆盖：带有 `std` 和至少一个已安装包的项目的映射形状；在带和不带 `fd` 的情况下按子字符串和 glob 查找；`rg` 与回退实现之间的 grep 正则表达式一致性、排名模式的排序及其 `truncated` 标志；按范围、按模块以及按定义（包括注解块）读取；以及 gan-mcp 对所有四种操作的转发。
