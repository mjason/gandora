# GEP-0031: 检索表面

## 摘要

在智能体编辑代码之前，它必须先找到代码。本 GEP 为 Gandora 提供了一个基于工具链已知信息构建的 AI 原生感知层：**代码地图**（`gan lsc map`）列出项目、标准库以及每个已安装包，并给出各自的源码路径和渲染头部；**文件名搜索**（`find`）和**内容搜索**（`grep`，支持正则表达式或 BM25 排序）基于一个包含项目源码、项目文档以及每个包随附的 `.gan` 源文件的语料库（GEP-0006）；**范围读取**（`read`）则获取一个代码块——按名称获取函数，或按路径加行范围获取——而不是整个文件。每项能力都是单个 `gan lsc` 查询，返回一个 JSON 值；`gan-mcp` 将全部四项作为工具转发，因此 shell 和 MCP 客户端看到相同的答案。

## 动机

通用检索栈会求助于 tree-sitter 和索引器；Gandora 则两者都不需要。编译器本身就是解析器（`symbols`、`wsymbols`、`definition` 已经返回名称、头部、行号和路径），而 GEP-0006 已经让每个发布的包都携带其 `.gan` 源码以供宏消费者使用——这意味着标准库和第三方依赖*天生可被源码搜索*，双语 `@doc` 说明文字也包括在内。所缺的是表层：一张供代理读取、以了解所有内容位置的地图，以及三个动词——find、grep、read——精确到代理永远不必将整个文件分页读入其上下文。

文档是有意作为语料库的一部分，而非事后补充：项目的 `docs/**/*.md` 和 README 回答了"我该如何使用这个"的问题，而这是任何符号表都无法回答的；`@doc`/`@moduledoc` 说明文字随已发布的 `.gan` 源码一同分发，因此一次 grep 就能在同一轮扫描中覆盖代码及其文档。

## 范围

`gan-lsc` 中的 `map`、`find`、`grep` 和 `read` 查询；语料库定义；可选的 `fd`/`rg` 加速及强制性回退机制；`gan-mcp` 中的四个转发工具。持久化索引、嵌入和跨项目搜索不在范围内。

## 术语

- **语料库（Corpus）**：检索操作所作用的文件集合（R002）。
- **依赖源（Dep sources）**：已安装包在其 `_gan/` 目录下随附的 `.gan` 文件，通过 `gandora.toml` 标记枚举。
- **块（Block）**：一个定义及其上方的注解行。

## 规范

**GEP-0031-R001：** 检索界面是四个 `gan-lsc` 查询——`map`、`find`、`grep`、`read`——每个查询在 stdout 上返回一个 JSON 值（GEP-0015-R001A）。`gan-mcp` MUST 将它们转发为工具 `gan_map`、`gan_search_files`、`gan_search_content` 和 `gan_read`，且不咨询任何模型（GEP-0028）。两个界面对同一问题返回相同的值。

**GEP-0031-R002：** 语料库按以下顺序构成：项目的 Gandora 源码（配置的源码根目录加上顶层 `tests/`）；项目的文档（根目录及 `docs/` 下的 `README*` 和 `*.md`，递归）；以及——在 `find`/`grep` 的 `--deps` 标志之后——每个已安装包的 `.gan` 源码，这些源码通过项目 `.venv` 下的 `gandora.toml` 标记发现（GEP-0006）。构建输出、缓存以及除依赖源码外的 `.venv` 内部内容永远不在语料库中。

**GEP-0031-R003：** `map` 返回图谱：对于项目，返回每个模块及其路径和渲染后的公共头部行；对于标准库和每个已安装包，返回每个模块及其随附 `.gan` 源码的路径和相同的渲染后头部行。一个头部行是一条概览行——签名后附加该定义的 `@doc` 第一句（`def map(xs, f) — Applies \`f\` to every element.`）——因此图谱一次拉取即可回答“这里有什么，它做什么”。图谱还列出文档文件。所有内容均会排序；项目内的路径使用项目相对路径，依赖路径使用绝对路径。`map <Mod>` 将图谱缩小到名称包含 `<Mod>` 的模块。

**GEP-0031-R004：** `find <pattern>` 匹配语料库中的文件*名称*（子串，或当模式带有 `*`/`?` 时为 glob）。当 `fd` 在 `PATH` 中时，它 MAY 加速项目遍历；纯回退实现 MUST 返回相同的集合。输出是排序后的路径列表。

**GEP-0031-R005：** `grep <pattern>` 搜索文件*内容*。默认模式是正则表达式，在存在 `rg` 时由其加速，并有一个形状相同的纯回退实现：按路径顺序返回 `{path, line, text}` 匹配列表。`grep --ranked <words>` 是面向自然语言文本的查询模式：文件使用 BM25 评分（k1 = 1.2，b = 0.75，整个文件作为文档，`[a-z0-9_]+` 词元，转为小写），答案为排名靠前的文件，每个文件附带其最佳匹配行。两种模式都会限制输出（200 个匹配；10 个排名文件），并且 MUST 通过 `truncated` 标志说明这一情况——静默截断会被当作完整。

**GEP-0031-R006：** `read` 恰好获取以下一种：`read <path> <from> <to>` —— 语料库文件中从 1 开始计数的闭区间行范围；`read <Mod>` —— 某个模块（项目或已安装）的完整源码；`read <Mod.fun>` —— 单个定义的代码块：其注解（`@doc`/`@param`/`@spec`/`@example`/自定义属性以及紧邻其上的注释）直到其最后一个子句，通过编译器自身的 `definition`/`symbols` 行数据定位，并以下一个符号为边界。答案包含 `{path, from, to, text}`，以便智能体能够引用并编辑它所读取的内容。

**GEP-0031-R007：** 确定性与封闭性：结果按顺序或按分数排列，并带有文档化的平局决胜规则（路径顺序），绝不依赖挂钟时间或环境；外部二进制文件只是优化项，绝不是必要条件；查询只读取文件和标记——无写入、无网络、无模型。

## 理由

一套实现，两个界面：查询逻辑放在 `gan-lsc` 中，因为语言智能已经在那里以 JSON 形式作答；`gan-mcp` 则转发而非重新实现，正如 doc 和 pack 工具那样（GEP-0026/0028）。BM25 采用真实公式，而非"相关性"式的空泛之谈，因为自行调优查询的智能体需要可预测的排序；选择整文件作为文档，使数学计算无需索引也保持严谨。`read` 的存在是因为智能体检索最昂贵的失败模式是：翻遍一个 600 行的文件只为使用其中 6 行——而编译器知道这 6 行在哪里。

## 向后兼容性

纯增量：四个新查询，四个新工具。

## 安全性与确定性

检索读取项目、其文档以及已安装的标记/源——这与编译器在构建时已经读取的信任域相同。`fd`/`rg` 使用固定的参数列表运行；它们的缺失改变的是性能，而非答案（R004/R005/R007）。

## 工具与 AI 使用

预期的循环：先运行一次 `gan_map` 确定方位；用 `gan_search_files` / `gan_search_content` 定位；用 `gan_read` 精确获取要更改的代码块；然后进入编写→`gan build`→`gan test` 的循环（GEP-0026）。简报和包保持提示词大小；地图则是更大的图集，由代理按需拉取。

## 已拒绝的替代方案

### Tree-sitter 语法与外部索引器

第二个解析器会偏离真正的解析器，而索引本质上是一个存在失效问题的缓存。编译器已经解析了语料库中的一切内容，并且包源码在 GEP-0006 之后已存在于磁盘上——在项目规模下，直接遍历这些源码已足够快。

### 编译产物搜索

搜索生成的 Python 会找到被修饰（mangling）后的名称，并且会遗漏宏和文档。`.gan` 源文件才是面向人类与智能体的权威产物；编译输出是为解释器准备的。

## 一致性

测试 MUST 覆盖：在包含 std 和至少一个已安装包的项目上的 map 形状；使用子字符串和 glob 的 find（分别在有和没有 `fd` 的情况下）；`rg` 与后备方案之间的 grep 正则表达式一致性、排名模式的排序及其 `truncated` 标志；按范围、按模块、按定义（包括注解块）的 read；以及所有四种的 gan-mcp 转发。
