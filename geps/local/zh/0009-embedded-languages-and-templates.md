# GEP-0009: 嵌入式语言与模板

## 摘要

嵌入式内容分为两个层级，每个层级都有其自身符号，与主体**是**什么相匹配：`~<lang>` 标记（`~markdown`、`~sql`、`~prompt` 等）是**文本**——带有语言标签的原始主体，求值为带有 `<%= expr %>` 值拼接的字符串；`$python(...)` 是**代码**——一个 Python 表达式，按字面方式进入程序，并带有代码拼接。数据不需要嵌入：Gandora 映射就是数据字面量。一种拼接机制覆盖了整个家族；符号让读者（以及 AI）一眼就能看出语义。

## Motivation

原始嵌入体（GEP-0005）有意抑制 `#{}` 插值，因为 `#` 和 `{` 在大多数目标语言中都有含义。但真正的嵌入内容需要参数——SQL 查询的表名、在 Gandora 绑定上计算片段的 Python 表达式、带值的 Markdown 报告。EEx 的 `<%= %>` 标记在实践中无冲突、熟悉，且在不同语言中表现一致。

## 范围

嵌入式 sigil 家族、`<%= %>`拼接和语言标记。
EEx 语句/循环标签（`<% %>`）、`.eex`模板文件、布局以及每种语言的验证被推迟。

## 术语

- **内嵌饰符**：其名称不属于 GEP-0005 内置饰符（`w`、`s`、`r`）的饰符；其名称即为语言标签。
- **拼接**：`<%= expr %>` 标记，包含一个 Gandora 表达式。

## Specification

**GEP-0009-R001:** 除内置符咒外，任何其他名称的符咒均为嵌入式符咒。其主体是原始的（遵循 GEP-0005-R002 反斜杠规则；无 `#{}` 插值）。GEP-0005-R009 中关于未知符咒的诊断规则被废除。语言标签是供工具（高亮、未来验证）使用的编译时元数据；编译器不解释主体语言。

**GEP-0009-R002:** 在每个嵌入主体内部，`<%= expr %>` 包含一个 Gandora 表达式，该表达式在符咒所在作用域内的绑定下进行解析和编译。标记内的空白字符被忽略；`<%%=` 转义字面量的 `<%=`。拼接 MUST 是单个表达式；解析失败会产生一个编译错误，指明该符咒。

**GEP-0009-R003:** 代码拼接的拼写是 **`$python(expr)`** —— `$` 是 Python 世界（GEP-0003），此形式是整个 Python 表达式而非模块成员。主体将逐字拼接到生成的代码中，作为一个表达式，每个 `<%= expr %>` 被替换为编译后的表达式文本（加括号）。这是唯一一个以代码形式进入程序的嵌入主体。`~python(...)` 仍然是有效的普通 R004 *文本* 符咒（主体标记为 python）；Advisor 会用 `$python` 配方标记它，以防作者本意是代码。

**GEP-0009-R004:** 所有其他嵌入式符咒都求值为字符串：主体文本中每个拼接被替换为表达式在运行时的值，格式化方式与 `#{}` 插值相同（当存在拼接时编译为 f-string，否则编译为普通字面量）。

**GEP-0009-R006:** `~p` 是 R004 的受认可拼写，用于面向 AI 模型的散文文本——它是 GEP-0005-R010 功能白名单中的一员，与 `~w ~s ~r` 并列：`~p(...)` 用于单行，`~p"""..."""` 用于块。主体是原始的——引号、花括号、反斜杠和 JSON 无需转义——而 `<%= expr %>` 仍然拼接值。工具会教授此名称；更长的标记如 `~prompt` 仍然是普通的 R004 文本符咒，语义相同。

**GEP-0009-R007（在修订版6中废除）：** `%json` 数据字面量在发布当天就被撤回：Gandora 映射（`%{}`）是唯一的数据拼写——更丰富（原子键、任意表达式）且已原生支持语言及其 AI 写作者。粘贴的 JSON 文档通过将 `:` 替换为 `=>` 成为映射；Advisor 会立即教给用户这种重写方式，运行时 JSON 文本使用 `$json.loads(s)`。一种数据写法胜过第二种更弱的写法。

**GEP-0009-R005:** 多行嵌入主体使用 GEP-0005 定界符，包括 `"""`；拼接方式完全相同。`"""` 主体遵循 GEP-0001-R026 的 heredoc 缩进缩减语义——开头的换行被丢弃，每行中与结束定界符缩进相等的部分被移除——因此模板可以在模块中自然缩进，同时生成左对齐的值。在该词法修剪之外，生成的输出 MUST 在拼接之外逐字节保留主体文本。

## 理由

一个用于所有语言的标记优于每种语言各自的插值规则，而 `<%= %>` 是 Elixir（EEx）中既定的写法。`~python` 的代码拼接与所有其他情况的值拼接，与每个主体的性质相匹配：`~python` 主体执行，其他主体是数据。无需验证的语言标签保持编译器小巧，同时为工具链提供稳定的挂钩。

## 向后兼容性

废除未知符号错误（附加的：之前被拒绝的程序现在变为有效）。包含文本 `<%=` 的 `~python` 主体必须切换为 `<%%=`；没有其他现有表面变化。

## 安全与确定性

拼接是普通的编译表达式；嵌入的主体在编译时保持为惰性文本。`~python` 保留其原有的审计面：由作者编写的代码在输出中可见。

## 工具与 AI 使用

智能体 SHOULD 使用 `~sql`/`~markdown`/等来处理嵌入内容，而不是拼接字符串，使用 `<%= %>` 进行参数化，并且永远不要从不可信字符串构建 `~python` 代码——拼接操作将 *值* 插入到其他语言中，但将 *代码* 插入到 Python 中。

## 被拒绝的替代方案

### 在嵌入体中启用 #{}

与目标语言语法冲突（`#` 注释、`{}` 块、Python 字典/集合显示）——这正是原始体存在的原因。

### 现在即实现完整的 EEx 引擎

语句标签、布局和文件模板是一个库级别的表面；值/代码拼接覆盖了语言层面的需求，未来的 GEP 可以在不改变此契约的情况下添加 `EEx` 类工具。

## 待解决的问题

此修订版无待解决的问题。

## 一致性

测试 MUST 覆盖：任意语言标签（sigil）求值得到其精确正文；值拼接（包括包含管道和互操作调用的表达式）编译为 f-字符串；`~python` 代码拼接；`<%%=` 转义；多行 `"""` 正文；单表达式诊断；以及拼接外部的字节保留。
