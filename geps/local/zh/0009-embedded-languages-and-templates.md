# GEP-0009: 嵌入式语言与模板

## 摘要

嵌入式内容分为三个层级，每个层级有其对应的符号，以匹配正文*本身*的性质：`~<lang>` 符号（`~markdown`、`~sql`、`~prompt` 等）是**文本**——带有语言标记的原始正文，通过 `<%= expr %>` 值拼接求值为字符串；`$python(...)` 是**代码**——一个逐字进入程序的 Python 表达式，支持代码拼接；`%json` 是**数据**——编译时解析的 JSON，作为纯字面量发出。一个拼接机制覆盖整个家族；符号能让读者（以及 AI）一眼看出语义。

## 动机

原始嵌入式主体（GEP-0005）故意抑制`#{}`插值，因为`#`和`{`在大多数目标语言中具有特定含义。但真正的嵌入式内容需要参数——SQL查询的表名、基于Gandora绑定且包含计算部分的Python表达式、带有值的Markdown报告。EEx的`<%= %>`标记在实践中无冲突、熟悉，且在不同语言中工作方式相同。

## 范围

嵌入式 sigil 系列、`<%= %>` 拼接和语言标记。
EEx 语句/循环标签（`<% %>`）、`.eex` 模板文件、布局和
按语言验证被延后。

## 术语

- **嵌入式标识符**：名称不是 GEP-0005 内置标识符（`w`、`s`、`r`）之一的标识符；其名称是语言标签。
- **拼接**：包含一个 Gandora 表达式的 `<%= expr %>` 标记。

## 规范

**GEP-0009-R001：** 名称不是内置符文的符石即为内嵌符石。其正文是原始的（GEP-0005-R002 反斜杠规则；无 `#{}` 插值）。GEP-0005-R009 中关于未知符石的诊断被废除。语言标签作为编译时元数据供工具使用（高亮、未来验证）；编译器不解释正文语言。

**GEP-0009-R002：** 在每个内嵌正文中，`<%= expr %>` 包含一个 Gandora 表达式，该表达式使用符石作用域内的绑定进行解析和编译。标记内的空白被忽略；`<%%=` 会转义原义 `<%=`。拼接 MUST 为单个表达式；解析失败是编译错误，错误信息会指明该符石。

**GEP-0009-R003：** 代码拼接写作 **`$python(expr)`** —— `$` 是 Python 世界（GEP-0003），此形式是整个 Python 表达式而非模块成员。正文被逐字拼接为生成代码中的单个表达式，每个 `<%= expr %>` 被替换为编译后的表达式文本（括号括起来）。它是唯一以代码形式进入程序的内嵌正文。`~python(...)` 仍作为普通的 R004 *文本*符石（正文标记为 python）有效；如果作者意图是代码，Advisor 会用 `$python` 配方标记它。

**GEP-0009-R004：** 所有其他内嵌符石求值为字符串：正文文本中每个拼接被替换为对应表达式的运行时值，格式化方式与 `#{}` 插值相同（当存在拼接时编译为 f-string，否则为普通字面量）。

**GEP-0009-R006：** `~prompt` 是 R004 用于面向 AI 模型的文本的推荐拼写：`~prompt(...)` 用于单行，`~prompt"""..."""` 用于块。正文是原始的——引号、花括号、反斜杠和 JSON 无需转义——但 `<%= expr %>` 仍可拼接值。工具（文档卡片、手册）会教授此名称；任何其他 R004 符石名称的行为相同。

**GEP-0009-R007：** 数据字面量以 **`%`** 拼写——数据字面量系列（`%{}` 映射、`%Mod{}` 结构体、`%json` JSON）。`%json(...)` / `%json"""..."""` 的正文在编译时由 GEP-0001-R018 JSONC 读取器解析（支持注释和尾随逗号，拒绝重复键），并发出等价的普通数据字面量——零运行时开销，格式错误的 JSON 是符石处的编译错误。拒绝拼接；动态结构使用普通映射构建。这使得工具架构和 API 载荷能够完全按照其 JSON 文档中的拼写粘贴。

**GEP-0009-R005：** 多行内嵌正文使用 GEP-0005 定界符，包括 `"""`；拼接工作方式相同。`"""` 正文遵循 GEP-0001-R026 的 heredoc 缩进剥离语义——开头的换行被丢弃，并且每行中与关闭定界符缩进相同的部分被剥离——因此模板可以在模块内部自然缩进，同时产生左对齐的值。在此词法修剪之外，生成的输出 MUST 在拼接之外逐字节保留正文文本。

## 理由

一种适用于所有语言的标记法优于每种语言各自的插值规则，而 `<%= %>` 是 Elixir 中已确立的写法（EEx）。`~python` 使用代码拼接，而其他所有情况使用值拼接，这与每个主体的本质相匹配：`~python` 主体执行代码，其他主体是数据。不带验证的语言标签保持了编译器的简洁，同时为工具提供了稳定的挂钩。

## 向后兼容性

废除未知符号错误（增量：先前被拒绝的程序变为有效）。包含字面文本 `<%=` 的 `~python` 正文必须切换为 `<%%=`；其他现有表面无变化。

## 安全性与确定性

拼接是普通的编译后表达式；嵌入的各部分在编译时保持为惰性文本。`~python` 保留其原有的审计面：作者编写的代码在输出中可见。

## 工具与 AI 使用

智能体应使用 `~sql`/`~markdown`/等表示嵌入内容，而非拼接字符串；使用 `<%= %>` 进行参数化，且绝不得从不可信字符串构建 `~python` 代码——拼接操作将 *值* 插值到其他语言中，但将 *代码* 插值到 Python 中。

## 被拒绝的替代方案

### 在嵌入体中使用 `#{}`

与目标语言语法冲突（`#` 注释、`{}` 块、Python 字典/集合显示）——这正是原始体存在的原因。

### 现在就用完整的 EEx 引擎

语句标签、布局和文件模板属于库级功能范围；值/代码拼接满足了语言层面的需求，未来的 GEP 可以在不改变本契约的前提下，在此之上添加 `EEx` 类工具。

## 开放问题

本修订版暂无。

## 符合性

测试 MUST 涵盖：任意语言标记求值为其精确主体；值拼接（包括包含管道和互操作调用的表达式）编译为 f-字符串；`~python` 代码拼接；`<%%=` 转义；多行 `"""` 主体；单表达式诊断；以及拼接外部的字节保留。
