## 摘要

本提案引入 **MCP 表面**，这是一种精炼的交互通道，将 Gandora 中部分通用工具执行语义提升为显式、可协商的协议表面。该表面面向那些希望以标准化方式公开、描述、暴露和协商其能力子集的工具——这些能力与模型上下文协议（Model Context Protocol，MCP）的客户端‑服务器语义保持一致。

与隐式的工具分发形成对比，MCP 表面是**显式声明**：工具宣称自己暴露了特定表面，每个表面定义一组受约束的调用模式、上下文先决条件和结果约定。

## 动机

随着工具的成熟，它们暴露出的能力越来越多，远超任何单一客户端实际所需。Gandora 的既有工具模型提供了一种统一机制，用于调用具备类型化参数和结构化结果的能力，但它不提供用于以下操作的框架性支持：

- **限制**：一个工具主动限制其能力范围，仅暴露一个小子集。
- **裁剪**：一个客户端只接受一个工具公开表面中的特定部分。
- **协商**：在执行之前，双方就能力、模式或协议的版本达成一致。
- **描述**：以机器可读与人类可读的方式对表面进行自描述。

MCP 表面通过对工具端点进行分组、封装和版本化来解决这些差距。

## 术语

| 术语 | 定义 |
|------|------------|
| MCP 表面 | 由 Gandora 工具暴露的一组受约束的、协商一致的调用能力。 |

| 表面契约 | 描述一个表面的机器可读声明，包括其端点、模式与限制。 |
| 表面协商 | 在调用之前，客户端与工具商定表面参数的过程。 |
| 表面上下文 | 供表面端点使用的预协商的状态或配置。 |
| 表面守卫 | 一个谓词，用于控制一个端点是否可用于给定的调用请求。 |
| 表面背面 | 一个工具中不属于任何已声明表面的部分，构成其隐式工具语义。 |

## 规格说明

### 1. 表面声明

一个工具 MUST 为其每个 MCP 表面发布一个表面契约。一个契约 MUST 包含人类可读的描述、版本字符串、端点列表以及一个可选的基础模式。

一个工具 MAY 声明多个 MCP 表面。如果工具声明了至少一个表面，则该工具 MUST NOT 在任一表面契约中暴露其全部能力；未包含在表面中的能力属于该工具的**表面背面**，并继续受既有工具语义的约束。

一个表面端点 MUST 是一个具名、可寻址的引用，其引用一个单一、确定的工具能力。一个端点 MUST NOT 引用多个能力。

一个表面版本 MUST 遵循语义化版本控制（Semantic Versioning）的约定。补丁级别的变更 MUST NOT 更改端点的语义；次要级别的变更 MAY 添加端点或放宽限制；主要级别的变更 MAY 移除端点或收紧限制。

### 2. 表面上下文

表面上下文是表面端点可用的预协商状态的集合。

一个工具 MAY 将一个表面上下文标记为必需或可选。如果某个端点需要该上下文，则该工具 MUST 在表面契约中包含对该上下文需求的说明；如果该上下文对于端点非必需，则该工具 SHOULD 将该上下文注明为可选。

上下文名称 MUST 在表面内唯一。上下文值 MUST NOT 在整个表面的生命周期内被隐式改变；任何更改 MUST 通过表面协商进行。

### 3. 表面协商

调用端点之前，客户端 MAY 通过表面协商流程与工具建立共同的表面参数。

协商流程 MUST 至少处理以下参数：

- 表面版本；
- 上下文绑定；
- 端点的子集选择；
- 限制条件。

工具 MUST 在下列情况下拒绝协商：所请求的版本不受支持、所请求的上下文绑定无效、或所请求的端点子集在当前工具状态下不可用。

工具 MUST NOT 在未收到明确协商确认的情况下，向任何客户端暴露超出当前协商参数之外的、额外的端点。

### 4. 表面端点

一个表面端点 MUST 声明一个参数模式。端点 MUST NOT 接受未在模式中定义的参数。

一个端点 MAY 声明前置条件。在这种情况下，该工具 MUST NOT 在前置条件不成立时执行该端点。

一个端点 MAY 声明后置条件。在这种情况下，该工具 MUST NOT 声明端点已成功完成，除非所有声明的后置条件都已满足。

一个端点 MUST NOT 修改预协商的上下文，除非表面契约明确允许这样做。

### 5. 表面守卫

表面守卫是一个谓词；当且仅当该谓词求值为 true 时，该端点才可被调用。

一个端点 MUST NOT 绕过其关联的守卫。一个守卫 MUST NOT 对端点产生副作用。

工具 SHOULD 在表面契约中以守卫的规范形式记录每个守卫。守卫逻辑 SHOULD 对客户端可审查；工具 SHOULD NOT 使用不透明的守卫。

当守卫失败时，工具 MUST 返回一个表明被阻止的调用的结果，并且 MUST NOT 执行该端点。

### 6. 表面背面

表面的背面包括工具所有未被协商表面所覆盖的能力。

关于背面的端点调用 MUST 遵循既有的工具语义。对背面的调用 MUST NOT 被记录为表面调用。

一个工具 MAY 提供一个**表面背面策略**，用于声明背面能力是否可被外部客户端枚举或发现。如果工具提供了这样的策略，则该策略 MUST 在表面契约中公开。

工具 SHOULD 在设计时尽量减少背面大小，但这并不改变规范：背面是隐式工具行为的合法部分。

### 7. 与既有工具语义的交互

表面的存在既不会改变一个工具对一般工具语义的遵从要求，也不会改变一个工具被呈现给 Gandora 的方式。

如果工具同时暴露表面和背面能力，则工具 MUST 提供一种方式，用于区分指向已协商表面中端点的调用请求与指向背面能力的调用请求。

负面案例：对表面上下文的修改 MUST NOT 对背面能力产生不可见的影响，除非这些影响已在表面契约中明确声明。

### 8. 已知的妥协

- 该协议增加了协议的重量：契约、协商和守卫都会增加实现和审计的复杂性。
- 表面是对能力的明确裁剪；对于某些工具来说，它们的全部能力已经是统一的，那么表面可能所提供的价值有限。
- 客户端可能会选择不进行协商，从而只能获得表面的默认快照，这可能不足以实现某些工作流程。

### 9. 示例

#### 9.1 表面契约

```yaml
surface: "filesystem"
version: "2.1.0"
description: "用于交互式编辑器集成的受限文件系统访问。"
base: "https://gandora.example/surfaces/filesystem"
endpoints:
  - name: "read"
    description: "读取单个文件。"
    params: { file: "string", offset: "integer" }
    guards: ["path-allowed", "size-limit"]
  - name: "write"
    description: "写入单个文件。"
    params: { file: "string", data: "string" }
    guards: ["path-allowed", "writable"]
context:
  required: ["working-directory"]
  optional: ["include-hidden"]
limits:
  max-read-size: 1048576
```

#### 9.2 协商请求

```json
{
  "protocol": "gep-0028-negotiation",
  "surface": "filesystem",
  "version": "2.x",
  "context": {
    "working-directory": "/tmp/gandora-demo"
  },
  "endpoints": ["read", "write"],
  "constraints": {
    "max-read-size": 65536
  }
}
```

  "accepted": true,

## 向后兼容性

本 GEP 不改变任何既有的工具语义。它增加了一个新的、可选的交互层。

实现本 GEP 的工具 MUST 保持其非表面行为与旧版 Gandora 兼容。本 GEP MUST NOT 要求更改底层的工具调度机制。

## 参考实现

参考实现位于 Gandora 核心仓库中，路径为 `gandora/surfaces`。该实现包含：

- 一个用于注册表面声明并验证其契约的注册表；
- 一个用于进行和验证协商的处理器；
- 一个用于执行涉及守卫的端点的执行器；
- 一个用于测试兼容性行为的验证套件。

## 摘要

`gan-mcp` 是一个用 Gandora 编写的 Model Context Protocol 服务器，将工具链暴露给任何 MCP 客户端。它承载着模型所需的答案——文档、上下文包、裁决——以及以往任何暴露面都无法给出的一个答案：**一个已经过编译、判定并真正运行的完整模块**。本 GEP 确立了整个暴露面所要强制执行的规则：未经运行的内容一律不返回。

## Motivation

GEP-0025 使修正变为一次调用，GEP-0026 使发现变为一次调用。两者都改进了模型*知道*的内容，但都没有改变模型*交付*的内容。模型仍然会编写一段代码，读回去，觉得它貌似合理，然后交给用户——而貌似合理并不是定论。观察到的失败并非对语法的无知，而是没有证据的自信：代码读起来正确，调用了一个并不存在的函数，却仍然到达了用户手中。

Gandora 处于异常有利的位置来弥补这一缺口。`@example` 不是装饰：它会编译成 `gan test` 执行的原生 Python doctest（GEP-0007）。因此，示例本身就是一种断言；带有示例的模块是一种可自我验证的产物。生成示例与测试示例是同一个行为；一个跳过后半段的表面是在主动选择（跳过）。

第二个理由是，服务器应当放在这里而不是客户端：MCP 从函数签名推导工具的 `inputSchema`，而 Gandora 从 `@spec` 推导签名，并从 `@doc`/`@param` 获取描述。Advisor 已经在执行的注解纪律正是该协议的元数据。合约只需编写一次。

## 范围

涵盖：stdio 服务器、其工具面、验证流水线，以及将需求转化为已验证模块的组合器。不在范围内：HTTP 传输、MCP 采样、简报之外的提示词和资源，以及包的发布（在本 GEP 被接受之前，发布链保持为五个包）。

## 术语

**Sandbox project** — 一个一次性项目，包含一个模块，每次请求时构建并丢弃。

**Atom** — 一个已验证的语言能力示例，来源于测试套件已运行的某个源。

**Composer** — 从需求到模块的模型驱动路径。

## Specification

**GEP-0028-R001 (服务器):** `gan-mcp` 通过 stdio 进行 MCP 通信，并且它本身就是一个 Gandora 程序。`GAN_MCP_ROOT` 选择其查询所应答的项目，默认为工作目录。

**GEP-0028-R002 (无未运行之物):** 每个含代码的答案 MUST 携带产生它的判定：诊断信息、实践建议，以及执行该模块 doctests 的结果。一个其模块未达到 `ok: true` 的答案 MUST 作为携带这些发现的失败返回。将未经验证的代码作为散文返回——无论看起来多么可信——都是该表面的缺陷，而非其降级模式。

**GEP-0028-R003 (流水线):** 验证将模块写入沙箱项目中其自身 `defmodule` 所要求的路径（GEP-0001-R013），其判定取自 `gan lsc check`（GEP-0025-R009），而非任何私有重实现，在硬性超时下执行编译产物的 doctests，并在之后移除沙箱。用户的项目绝不会被写入。

**GEP-0028-R004 (模式不会被写两次):** 工具输入从 `@spec` 派生，描述来自 `@doc` 和 `@param`。工具函数 MUST NOT 接受默认参数，因为默认参数会抹除生成的签名，并且 MUST 携带足够精确的 spec，以作为公共契约。

**GEP-0028-R005 (零成本工具):** `gan_doc`、`gan_pack`、`gan_check` 和 `gan_briefing` 转发已经存在的表面（GEP-0015、GEP-0025、GEP-0026），且 MUST NOT 调用模型。无法凭空编造的内容 MUST NOT 被编造。

**GEP-0028-R006 (组合器解释并演示):** `gan_example` 接受一个要演示的特性、语法或能力，并返回两样东西：一段散文式**解释**，以及一个**完整模块**——包含 `defmodule` 与 `@moduledoc`，并且对每个公共函数都包含 `@doc`、`@param`、`@spec` 和至少一个 `@example` doctest——该模块已通过 R002。它 MUST NOT 返回裸片段：片段无法编译、无法进行 doctest，也无法成为原子，因此根本无法被验证。**答案中的每一行代码 MUST 存在于已验证模块中。** 解释中的代码将是伪装成已验证声明的未验证声明，因此该表面会将其移除。

**GEP-0028-R007 (生成前先进行事实锚定):** 组合器的提示 MUST 携带上下文包和与该需求相关的原子。模型被要求依据所提供的事实进行组合，绝不去回忆语言。

**GEP-0028-R008 (判定驱动努力):** 组合器在首次尝试时以禁用推理的方式运行。失败判定——而非对难度的猜测——才会提高下一次尝试的努力程度。轮次有上限；当最后一轮失败时，该表面返回这些发现和最接近的已验证原子，绝不返回最后一份草稿。

**GEP-0028-R009 (原子是挣得的):** 一个原子 MUST 来自测试套件会运行的来源——一个 std 或 tour 的 `@example`，或者一个通过 R002 的组合模块。一个通过验证的组合 MAY 被记录为原子；记录它并不会让它在被提供时免于重新验证。

**GEP-0028-R010 (执行模型编写的代码):** 沙箱会运行服务器未编写的代码。它 MUST 在临时目录中执行并设有超时，MUST NOT 让用户项目访问到它，且其失败 MUST 以判定形式呈现，而不是作为异常跨越协议边界。

**GEP-0028-R011 (凭据):** 模型配置来自环境变量（`GAN_API_KEY`、`GAN_MODEL`，以及一个可选的 `GAN_BASE_URL`，默认指向供应商端点）。凭据 MUST NOT 被记录到日志、回显到判定中，或被写入沙箱。

## Rationale

这个表面拒绝了大多数代码生成工具所接受的拆分——一条从模型得到答案的快速路径和一条执行检查的慢速路径。在这里，检查*就是*答案：带有通过的 doctest 且 `clean: true` 的判定，是让这个服务器区别于一个读过手册的模型的唯一因素。让这一点不可协商（R002），才能让智能体将结果直接交给用户。

R006 选择模块而不是片段，因为模块是工具链能够判断的最小单元。片段读起来更短，却无法验证；多出来的那些行就是证据。将答案一分为二，正是语言已经应用到自身文档上的同一原则：`@doc` 是散文，`@example` 会被执行，二者不可兼得。

驱动 composer 的提示词本身就是用该语言的提示语法编写的——`~p"""` 带有 `<%= %>` 拼接（GEP-0009-R006）——并且它不携带任何手写的模块模板。答案的形状由测试套件编译并运行的语料库模块展示，因此这条流水线中唯一没有人验证过的代码并不存在。

R008 颠倒了通常的推理预算问题。当循环中存在一个基于真值的验证器时，一次带有真实诊断信息的迭代，比针对同一个猜测进行更深入思考能教会我们更多——因此努力跟随失败，而不是预先估计失败。

## 安全性与确定性

沙箱执行生成的代码，这与 `gan run` 已经代表用户跨越的信任边界相同，但范围已收窄：临时目录、硬超时、无网络要求、事后移除。对于未更改的工具链，已验证的答案是可重现的——判定结果和 doctest 输出是关于产物的事实，而非关于起草它的模型的事实。

## 工具与 AI 使用

MCP 客户端 SHOULD 每次会话调用一次 `gan_briefing`，调用 `gan_doc` 或 `gan_pack` 以理解含义，并对其打算交付的每个模块运行 `gan_verify`——包括它自己编写的模块。`gan_example` 适用于需求明确但形式不明确的情况。

## Conformance

测试 MUST 覆盖：一个正确模块在 doctests 运行并通过后达到 `ok`/`clean`；一个模块调用不存在的 std 函数并以 artifact 诊断失败；一个模块预期 doctest 输出错误、编译 clean 但 doctest 失败；模块名到沙箱路径的推导（包括点分名称）；从 `@spec` 推导出的工具 schema；每个语料库模块都应通过其自身所教导的同一判定；以及 composer 要么返回一个解释外加一个通过了 R002 的模块，要么返回携带发现项的失败——决不返回未经验证的草稿。
