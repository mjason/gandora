# GEP-0028：MCP 表面

## 摘要

本 GEP 定义了 Gandora 的 MCP（模型上下文协议）表面。MCP 表面由一组工具、资源和提示组成，Gandora 通过 MCP 将其暴露给 AI 客户端。本提案对 MCP 表面进行了规范化，使其可被发现、可预测且稳定，从而使 AI 客户端能够以可靠的方式与 Gandora 交互。

## 动机

随着 AI 驱动的开发工具日益增多，Gandora 需要一种标准化方式，让 AI 客户端能够与项目元数据、构建系统和开发工作流进行交互。虽然 Gandora 的命令行界面功能强大，但它专为人类交互而设计，并未针对 AI 代理的使用进行优化。MCP 提供了一种标准协议，使 Gandora 能够以结构化、机器可读的方式暴露其能力。

如果没有规范化的 MCP 表面，AI 客户端将不得不：
- 解析人类可读的命令行输出，这种方式既脆弱又容易出错。
- 依赖未文档化且可能发生变化的内部接口。
- 无法发现 Gandora 的能力，除非另行告知。

通过定义稳定的 MCP 表面，我们使 AI 客户端能够自然地发现并使用 Gandora 的功能，正如人类用户通过 `gandora --help` 发现 CLI 一样。

## 设计

MCP 表面由三个主要组件构成：工具、资源和提示。每个组件都服务于不同的目的，并遵循特定的约定。

### 工具

工具是可由 AI 客户端调用的可执行操作。每个工具都有一个名称、描述和输入模式。工具可用于执行构建、运行测试和管理项目依赖。

GEP-0028-R001：Gandora MUST 将以下工具暴露给 MCP 客户端：

| 工具名称 | 描述 | 输入模式 |
|---------|-------------|------------|
| `gandora.build` | 构建当前项目 | `{ "target"?: string, "mode"?: "debug" \| "release" }` |
| `gandora.test` | 运行测试套件 | `{ "filter"?: string, "jobs"?: number }` |
| `gandora.run` | 运行项目可执行文件 | `{ "args"?: string[], "env"?: Record<string, string> }` |
| `gandora.deps.add` | 向项目添加依赖 | `{ "spec"?: string, "dev"?: boolean }` |
| `gandora.deps.remove` | 从项目中移除依赖 | `{ "name": string }` |
| `gandora.deps.list` | 列出项目依赖 | `{ "kind"?: "all" \| "prod" \| "dev" }` |
| `gandora.check` | 检查项目中的错误 | `{ "target"?: string, "all-targets"?: boolean }` |
| `gandora.format` | 格式化项目源代码 | `{ "check"?: boolean, "files"?: string[] }` |
| `gandora.lint` | 对项目运行 linter | `{ "fix"?: boolean, "files"?: string[] }` |

GEP-0028-R002：每个工具 MUST 返回符合其工具描述的 JSON 编码结果。

GEP-0028-R003：工具名称 MUST 使用由句点分隔的小写蛇形命名法（例如 `gandora.deps.add`）。

GEP-0028-R004：工具描述 MUST 为动词短语，描述工具执行的操作（例如“构建当前项目”）。

### 资源

资源是可供 AI 客户端读取的结构化数据片段。资源具有 URI 和文本或二进制内容。资源用于暴露项目元数据和配置。

GEP-0028-R005：Gandora MUST 将以下资源暴露给 MCP 客户端：

| 资源 URI | 描述 | 内容类型 |
|-----------|-------------|-----------------|
| `gandora://project/manifest` | 项目清单（例如 `gandora.toml`） | `application/toml` |
| `gandora://project/tree` | 项目文件树的摘要 | `application/json` |
| `gandora://project/config` | 活动配置设置 | `application/json` |
| `gandora://project/targets` | 可用构建目标 | `application/json` |
| `gandora://project/deps` | 依赖图 | `application/json` |

GEP-0028-R006：资源 URI MUST 遵循 `gandora://` 方案，后跟点分隔的路径段。

GEP-0028-R007：资源内容 MUST 使用资源的 `content_type` 字段中指定的媒体类型进行编码。

### 提示

提示是预定义的提示模板，AI 客户端可以使用它们来生成操作序列。提示用于为常见工作流提供结构化指导。

GEP-0028-R008：Gandora MUST 将以下提示暴露给 MCP 客户端：

| 提示名称 | 描述 | 参数 |
|-----------|-------------|------------|
| `gandora.setup-project` | 初始化新项目的工作流 | `{ "name": string, "template"?: string }` |
| `gandora.add-dependency` | 添加依赖并验证其兼容性的工作流 | `{ "spec": string, "dev"?: boolean }` |
| `gandora.release` | 发布新版本的工作流 | `{ "version"?: string, "dry-run"?: boolean }` |

GEP-0028-R009：提示 MUST 返回一个消息列表，指导 AI 客户端完成所请求的工作流。

## 配置

MCP 表面通过在 `gandora.toml` 中的 `[mcp]` 部分进行配置。

GEP-0028-R010：Gandora MUST 支持 `[mcp]` 配置部分中的以下键：

| 键 | 类型 | 默认值 | 描述 |
|-----|------|---------|-------------|
| `enabled` | `bool` | `true` | 是否启用 MCP 服务器 |
| `host` | `string` | `"127.0.0.1"` | 要绑定的主机地址 |
| `port` | `uint16` | `0` | 要绑定的端口（`0` = 自动选择） |
| `allow` | `string[]` | `["*"]` | 允许的工具、资源和提示列表 |
| `deny` | `string[]` | `[]` | 拒绝的工具、资源和提示列表 |

GEP-0028-R011：如果同时指定了 `allow` 和 `deny`，Gandora MUST 应用 `deny` 列表，然后再应用 `allow` 列表。

GEP-0028-R012：Gandora MUST 拒绝任何未明确包含在 `allow` 列表中（或由 `"*"` 通配符匹配）且未被 `deny` 列表排除的工具、资源或提示的访问。

## 错误处理

MCP 表面定义了标准化错误，使得 AI 客户端能够一致地从故障中恢复。

GEP-0028-R013：工具调用失败时 MUST 返回一个 JSON-RPC 错误，并符合以下代码：

| 代码 | 名称 | 描述 |
|------|------|-------------|
| `-32001` | `ToolNotFound` | 请求的工具不存在 |
| `-32002` | `ToolExecutionError` | 工具在执行过程中失败 |
| `-32003` | `InvalidParams` | 提供给工具的参数无效 |
| `-32004` | `PermissionDenied` | 工具被 `deny` 列表拒绝 |
| `-32005` | `ResourceNotFound` | 请求的资源不存在 |

GEP-0028-R014：错误响应 MUST 在 `data` 字段中包含人类可读的消息，以及（在适用时）工具或资源名称。

GEP-0028-R015：Gandora MUST NOT 在错误响应中暴露内部堆栈跟踪，除非 `gandora.toml` 中的 `[mcp]` 部分设置了 `debug = true`。

## 版本控制

MCP 表面遵循语义化版本控制。主版本号变更表示不兼容的协议更改；次版本号变更表示向后兼容的添加；补丁版本号变更表示向后兼容的修复。

GEP-0028-R016：Gandora MUST 在 MCP 握手期间暴露其 MCP 表面版本。

GEP-0028-R017：Gandora MUST 保持向后兼容性，直到发布带有新主版本号的 MCP 表面。

## 安全性

MCP 表面将 Gandora 的操作暴露给可能不受信任的 AI 客户端。安全至关重要。

GEP-0028-R018：Gandora MUST 仅将 MCP 服务器绑定到 `127.0.0.1`，除非用户在配置中明确覆盖。

GEP-0028-R019：Gandora MUST 在运行时验证所有工具输入，并拒绝任何格式错误的输入，且 MUST NOT 部分执行。

GEP-0028-R020：工具 `gandora.deps.add` 和 `gandora.deps.remove` MUST 要求由 MCP 客户端在工具调用中显式确认。

## 与 CLI 的关系

MCP 表面有意与 CLI 并行。两者共享底层实现，但暴露不同的接口。

GEP-0028-R021：MCP 表面 MUST NOT 引入不在 CLI 中可用的功能。

GEP-0028-R022：CLI 和 MCP 表面 MUST 在功能上保持一致，使得工具调用产生与等效命令行调用相同的结果。

## 测试

GEP-0028-R023：Gandora MUST 为 MCP 表面的每个工具、资源和提示提供集成测试。

GEP-0028-R024：集成测试 MUST 验证工具结果、错误响应的正确性，以及 `allow`/`deny` 配置的正确应用。

## 兼容性

GEP-0028-R025：MCP 表面 MUST 要求 MCP 协议版本为 1.0 或更高。

GEP-0028-R026：Gandora MUST 优雅地处理来自不支持功能的 MCP 客户端的请求，通过返回 `MethodNotFound` 错误代码。

## 未来工作

以下领域已确定，但不在本 GEP 范围内：

- 流式工具执行，用于长时间运行的构建和测试。
- 用于增量项目更新的订阅式资源通知。
- 用于远程协作的安全工具执行。
- 用于自定义工作流的用户定义工具。

## 备选方案

### 仅通过 CLI 暴露

我们考虑了仅依赖 CLI 与 AI 客户端交互的方案。该方案被否决，因为解析命令行输出是脆弱的，并且无法进行能力发现。

### 自定义协议

我们考虑了为 Gandora 定义自定义 AI 交互协议。该方案被否决，因为 MCP 正迅速成为 AI 客户端与工具交互的事实标准，而自定义协议需要客户端提供额外支持。

### 进程内嵌入

我们考虑了提供进程内嵌入式 API 的方案。该方案被否决，因为进程内嵌入要求 AI 客户端在与其相同的进程中运行 Gandora，而 MCP 支持进程外通信。

## 未解决的问题

- 资源缓存策略：应缓存哪些资源、缓存多久？
- 工具超时：长时间运行的调用应在何时失败？
- 多项目配置：一个 MCP 服务器应在单个工作区内暴露多个项目吗？

## 摘要

`gan-mcp` 是一个模型上下文协议（Model Context Protocol）服务器，用 Gandora 编写，
将工具链暴露给任何 MCP 客户端。它承载模型所需的答案——文档、上下文包、判定——
以及一个之前任何界面都无法给出的答案：**一个已经被编译、判定并真正运行过的完整模块**。
本 GEP 确立了整个界面存在所要执行的规定：任何未经运行的内容都不得返回。

## 动机

GEP-0025 将修正变成了一次调用，GEP-0026 将发现变成了一次调用。两者都改善了模型所*知道*的内容；但都未改变模型所*交付*的内容。模型仍然会写出一段代码，读回检查，觉得它貌似合理，然后交给用户——而貌似合理并不是定论。所观察到的失败并不是不懂语法，而是没有证据的自信：代码读起来正确，调用了一个不存在的函数，却仍然到达了用户手里。

Gandora 在解决这个问题上具有非同寻常的优势。`@example` 不是装饰：它编译成一个由 `gan test` 执行的原生 Python doctest（GEP-0007）。因此，示例本身就是一项断言；携带示例的模块是一个自验证的工件。生成示例与测试示例是同一个行动；任何跳过后半部分的表层都是在刻意选择如此。

服务端属于这里而非客户端的第二个原因是：MCP 从函数签名推导出一个工具的 `inputSchema`，而 Gandora 从 `@spec` 推导出签名，并从 `@doc`/`@param` 推导出描述。Advisor 已经在执行的注解纪律正是该协议的元数据。契约一次写成。

## 范围

涵盖：stdio 服务器、其工具表面、验证流水线、将需求转化为已验证模块的组合器，以及将该组合器接入读取需求的智能体的项目级配置。范围外：HTTP 传输、MCP 采样，以及简报之外的提示词和资源。

## 术语

**沙盒项目** — 一个临时项目，包含一个模块，按照每个请求构建并丢弃。

**原子** — 针对单一语言能力的已验证示例，取自测试套件已运行的来源。

**组合器** — 从需求到模块的、由模型支持的路径。

## 规范

**GEP-0028-R001（服务器）：** `gan-mcp` 通过 stdio 使用 MCP 协议，并且它本身就是一个 Gandora 程序。`GAN_MCP_ROOT` 选择其查询所针对的项目，默认使用当前工作目录。

**GEP-0028-R002（无不经运行之物）：** 每个包含代码的回答 MUST 携带产生该回答的裁决：诊断信息、实践建议，以及执行该模块 doctest 的结果。若某回答的模块未达到 `ok: true`，则 MUST 作为携带这些发现的失败结果返回。将未经验证的代码作为散文返回——无论看起来多么合理——都是此界面的缺陷，而非其降级模式。

**GEP-0028-R003（流水线）：** 验证过程将该模块写入沙箱项目中其自身 `defmodule` 所要求的路径（GEP-0001-R013），从 `gan lsc check`（GEP-0025-R009）获取裁决，而非任何私有的重新实现，在硬超时下执行编译产物的 doctest，并在之后移除沙箱。用户的项目永不被写入。

**GEP-0028-R004（模式不写两遍）：** 工具输入来自 `@spec`，描述来自 `@doc` 和 `@param`。工具函数 MUST NOT 使用默认参数，因为默认参数会抹掉生成的签名，并且 MUST 携带足以作为公共契约的精确 spec。

**GEP-0028-R005（零成本工具）：** `gan_doc`、`gan_pack`、`gan_check` 和 `gan_briefing` 转发已存在的界面（GEP-0015、GEP-0025、GEP-0026），且 MUST NOT 咨询模型。无法发明的内容就 MUST NOT 被发明。

**GEP-0028-R006（作曲者解释并演示）：** `gan_example` 接收一个要演示的特性、语法或能力，并返回两样东西：一段散文式**解释**，以及一个**完整模块**——包含 `defmodule` 与 `@moduledoc`，并且对每个公共函数包含 `@doc`、`@param`、`@spec` 以及至少一个 `@example` doctest——且该模块已通过 R002。它 MUST NOT 返回裸片段：片段无法编译、无法进行 doctest、也无法成为原子，因此完全无法被验证。**回答中的每一行代码 MUST 位于已验证的模块内。** 解释中的代码会是伪装成已验证主张的未验证主张，因此该界面会将其剥离。

**GEP-0028-R007（先接地，后生成）：** 作曲者的提示 MUST 携带上下文包以及与需求相关的原子。模型被要求依据提供的事实进行创作，绝不去回忆这门语言。

**GEP-0028-R008（裁决驱动投入）：** 作曲者在首次尝试时禁用推理运行。失败裁决——而非对难度的猜测——才会提高下一次尝试的投入。轮次有上限；当最后一轮失败时，该界面返回发现结果和最接近的已验证原子，绝不返回最后一版草稿。

**GEP-0028-R009（原子是挣来的）：** 原子 MUST 来自测试套件会运行的来源——即 std 或 tour 的 `@example`，或一个已通过 R002 的作曲模块。一个成功的作曲结果 MAY 被记录为原子；记录它并不免除其在被提供时重新验证的义务。

**GEP-0028-R010（执行模型编写的代码）：** 沙箱运行服务器未编写的代码。它 MUST 在临时目录中于超时限制下执行，MUST NOT 可从用户的项目访问，并且其失败 MUST 作为裁决呈现，而非作为跨越协议边界的异常。

**GEP-0028-R011（凭据）：** 模型配置来自环境（`GAN_API_KEY`、`GAN_MODEL`，以及可选的 `GAN_BASE_URL`，默认指向供应商端点）。凭据 MUST NOT 被记录、回显到裁决中，或写入沙箱。

**GEP-0028-R012（项目拥有接线）：** `gan init` MUST 写入每个代理自行读取的项目级 MCP 配置，采用该代理文档规定的形状和位置——Claude Code 为 `.mcp.json`，Codex 为 `.codex/config.toml`，opencode 为 `opencode.json`——并且 MUST NOT 覆盖已存在的文件。每个这样的文件声明同一条无路径命令 `uv run gan mcp`：没有 `cwd`，没有绝对路径，没有环境变量。`uv run` 从客户端启动的任何位置解析项目环境，`gan` 在该项目的 `.venv/bin` 中找到 `gan-mcp`（GEP-0013-R003），服务器通过向上查找到最近的 `gandora.jsonc` 来发现项目。因此 `gandora-mcp` 是每个脚手架项目的开发依赖。这些文件本应被提交：一旦入库，接线对每个克隆项目的人都有效，并且它们产生的裁决属于该项目自身，在其自身环境内被评判，而不是由恰好系统级安装的任何工具链评判。

**GEP-0028-R012A（代理指令以同样方式接线，修订版 4）：** `gan init` 也接入代理指令文件。当两者都不存在时，它会创建 `AGENTS.md`，其中包含以标记分隔的 Gandora 区块——一份紧凑的指针文档（循环、检索优先的习惯、`gan_verify` 作为唯一证明，以及实时简报所在位置），绝不是工具链已经提供的规则的副本。当 `AGENTS.md` 存在时，该区块会被追加，其标记使操作幂等；用户自己的内容永不被触碰。当 `CLAUDE.md` 存在时，会（仅一次）追加一行 `@AGENTS.md` 导入，以便 Claude 读取同一区块。静态接线仍然是 `gan init` 的职责——可重跑、确定性、对变更诚实——而 MCP 服务器保持其永不在项目中写入的特性：它的 `instructions` 可以引导代理执行 `gan init .`，而不是替它完成写入。

## 理由

该表面拒绝了大多数代码生成工具接受的分裂——一条从模型得到答案的快速路径，一条进行检查的慢速路径。在这里，检查*就是*答案：带有通过 doctests 的 `clean: true` 裁决，是这台服务器与一台已阅读手册的模型之间的唯一区别。将这一点设为不可协商（R002），才能让代理把结果直接交给用户。

R006 选择模块而非片段，因为模块是工具链能够判断的最小单元。片段读起来更短，却无法验证；多出的几行就是证据。将答案一分为二，正是该语言已经应用于自身文档的同一原则：`@doc` 是散文，`@example` 是被执行的代码，没有任何内容可以同时兼任两者。

驱动组合器的提示词本身正是用该语言的提示词语法编写的——`~p"""` 结合 `<%= %>` 拼接（GEP-0009-R006）——且其中不携带任何手写的模块模板。答案的形状由测试套件编译并运行的语料库模块展示，因此，流水线中那个无人验证的代码片段并不存在。

R008 颠倒了常见的推理预算问题。当循环中有真值验证器时，一次携带真实诊断的迭代，比在同一个猜测上做更深入的思考教给我们的更多——因此，投入要紧随失败，而不是预判失败。

## 安全性与确定性

沙箱执行生成的代码，这与 `gan run` 代表用户已经跨越的信任边界相同，但范围更窄：临时目录、硬超时、无网络需求、事后移除。在工具链不变的情况下，已验证的答案是可复现的——判定结果和 doctest 输出是关于工件的事实，而非关于生成该工件的模型。

## 工具与 AI 使用

MCP 客户端 SHOULD 在每个会话中调用一次 `gan_briefing`，调用 `gan_doc` 或 `gan_pack` 以了解含义，并对其打算移交的每个模块调用 `gan_verify`——包括它自己编写的模块。`gan_example` 适用于需求明确但形态不明确的情况。

## 符合性

测试 MUST 覆盖：一个正确的模块达到 `ok`/`clean` 状态，且 doctests 已运行并通过；一个调用不存在的标准库函数的模块，以工件诊断失败；一个预期 doctest 输出错误但编译干净的模块，却在 doctests 中失败；从模块名到沙箱路径的推导（包括点分名称）；从 `@spec` 派生的工具 schema；每个语料库模块都能承受它自身所教导的同一判定；以及组合器要么返回一个解释外加一个通过 R002 的模块，要么返回带有发现的失败——绝不返回未经验证的草稿。
