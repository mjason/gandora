# GEP-0029: 任务

## 摘要

`Task` 是 Gandora 在 Python 协程世界之上的库：`run` 从同步边缘进入，`async` 生成，语言自身的 `await`（GEP-0030）汇合，而高于裸汇合的一切——带元组判定的截止时间、有序扇出、有界流、组合子、取消、通往阻塞代码的桥梁——是一个普通的标准模块，由薄的 `asyncio` 包装组成。一个世界，说得直白些：线程不再是并行的 Task 宇宙，而只是这个宇宙内部的 `blocking` 桥梁。

## Motivation

修订版 1–4 在 `concurrent.futures` 之上构建了 Task：一套 Elixir 形态的线程池词汇表，通过 `from_async` 桥接将协程强压到隐藏的后台事件循环上。它能工作，但其代价是结构性的：一个守护线程持有不可见的循环；anyio 的单任务生命周期限制了能穿越桥接的内容；一整套诚实但丑陋的脚注（“运行中的线程无法被杀死”）；以及——当 GEP-0030 修订版 3 在其上叠加 `@async` 之后——一套在不同世界中编译方式各异的词汇表。

Gleam 指出了这个错误：每个目标的库都以单薄的方式暴露该目标的原生模型（`gleam/javascript/promise` 包装了 JS 已有的 Promise），没有任何一个世界模拟另一个世界。现代 Python 从另一侧得出了相同的结论——其自身的指导原则是将 asyncio 用于结构、用 `to_thread` 处理阻塞边界，而不是将线程池作为主要模型。随着原生 `async def`/`await` 进入语言（GEP-0030 修订版 4），线程世界不再承担承重角色：Task 回归协程世界的自然形态，它保留的每个包装器都是覆盖在 `asyncio` 之上的一行可读代码。

Task 相对于原始 asyncio 互操作所增加的东西，才是值得拥有的 API：返回 `{:ok, v}` / `{:error, :timeout}` 元组而不是抛出异常的毫秒级截止时间、有序连接、有界流、Gleam 的组合子，以及真正执行取消的取消机制——而线程永远无法做到这些。

## 范围

涵盖：`Task` 标准模块 — `run/1`, `async/1`, `blocking/1`,
`all/1`, `try_await/2`, `try_all/2`, `async_stream/3`, `map/2`,
`tap/2`, `recover/2`, `race/1`, `shutdown/1`, `sleep/1`,
`completed/1`。不在范围内：其所依赖的语法（GEP-0030）、
监督与链接（BEAM 属性；asyncio 没有对应物，也不进行模仿），
以及作为面向用户模型的线程池 — 阻塞工作通过 `blocking/1` 进入，
而不是通过第二个 Task。

## 术语

**Task** — 对已派生工作的句柄；具体而言是一个 `asyncio.Task`。

**Coroutine** — 调用异步函数所返回的对象；在被等待（await）或派生之前处于惰性状态。

**The rim** — 协程世界外围的同步代码；它通过 `run/1` 进入。

## 规范

**GEP-0029-R001 (run):** `Task.run(coro)` 从同步代码将一个协程运行至完成，并返回其值——原样等同于 `asyncio.run`。它是唯一允许在 async 函数体之外使用的 Task 函数；入口点 `main` 保持同步（GEP-0030-R001）：程序的异步部分全部挂在唯一一次 `run` 之下。

**GEP-0029-R002 (async):** `Task.async(coro)` 将协程生成为一个与其调用者并发运行的任务，并返回句柄——`asyncio.ensure_future`。汇合是语言自身的 `await t`，没有包装，也没有截止时间。没有被 await 的任务会静默失败：去 await 那些你需要看到失败的任务。

**GEP-0029-R003 (blocking):** `Task.blocking(fun)` 返回一个协程，该协程在工作线程上运行零参数的阻塞函数 `fun`——原样等同于 `asyncio.to_thread`。await 它以获取值，或者用 `async/1` 生成它，使阻塞工作与协程重叠执行。这就是线程在 Task 中仅剩的角色：边缘处的桥梁，而非一个世界。

**GEP-0029-R004 (try_await):** `Task.try_await(task, timeout)` 以 `timeout` **毫秒**为截止时间进行汇合（Elixir 的单位），返回判定而不是抛出异常：任务完成时返回 `{:ok, value}`；截止时间耗尽时返回 `{:error, :timeout}`——任务随后被**取消**，这正是 asyncio 自身 `wait_for` 的语义；在线程只能耸耸肩之处，这种处理是诚实的——以及当它抛出异常时返回 `{:error, error}`（异常作为值）。timeout 是必需的：无截止时间的汇合就是裸 `await`；隐藏默认值正是本 GEP 代价最昂贵的教训。

**GEP-0029-R005 (all / try_all):** `Task.all(tasks)`——被 await 后——按输入顺序返回这些值；某个任务崩溃会在汇合处重新抛出。其实现形式就是顺序汇合 `[await t for t in tasks]`：任务已经并发运行，因此按顺序汇合不费任何成本，而且读起来与它的实际行为完全一致。`Task.try_all(tasks, timeout)` 施加一个以 `timeout` 毫秒为限的组级截止时间，并按顺序为每个任务返回一个 R004 判定。

**GEP-0029-R006 (async_stream):** `Task.async_stream(xs, fun, max_concurrency \\ 8)`——被 await 后——将 `fun` 应用于每个元素，同时最多运行 `max_concurrency` 个，并按输入顺序返回结果。`fun` MUST 返回一个可等待对象（调用 async 函数，或对阻塞函数使用 `blocking/1`）；这个上限是一个信号量，在实现中可见。

**GEP-0029-R007 (combinators):** 仿照 Gleam 的 promise 模块，有四个不汇合的组合子。`map`、`tap` 和 `recover` 返回一个**惰性可等待对象**——一种可以在任何地方组合的协程：await 它，用 `async/1` 生成它，或把它交给 `run/1`。正是惰性使得组合子链可以在边缘处构建、稍后再运行：

- `Task.map(task, fun)`——`fun(value)` 的可等待对象；崩溃会原样传播。
- `Task.tap(task, fun)`——为副作用运行 `fun(value)`，并将原值传递下去。
- `Task.recover(task, fun)`——当 `task` 崩溃时，是 `fun(error)` 的可等待对象；未崩溃时，则是该值的可等待对象（Gleam 写作 `rescue`；`rescue` 是 Gandora 的关键字）。
- `Task.race(tasks)`——被 await 后——以第一个落定的任务为准，无论结果是值还是崩溃；其余任务继续运行。

链式组合（`promise.await` 的 flatMap）仍然不存在：在两次汇合之间，Gandora 就是普通代码。

**GEP-0029-R008 (shutdown):** `Task.shutdown(task)` 请求取消，并返回该请求是否生效。与线程不同，正在运行的协程任务确实会被中断——取消正是这个异步世界之所以正确的理由之一。

**GEP-0029-R009 (sleep / completed):** `Task.sleep(ms)`——被 await 后——暂停当前协程而不阻塞事件循环。`Task.completed(value)` 是一个已经持有 `value` 的协程，用于那些必须统一返回可等待对象的 API。

**GEP-0029-R010 (zero runtime):** `Task` 是一个用 Gandora 编写的普通标准库模块——它本身就使用它所依托的 GEP-0030 语法。每个函数都是对 `asyncio` 的一层薄而可读的包装；没有调度器、没有包装类、没有后台线程、没有模块状态。

**GEP-0029-R011 (determinism in tests):** 一致性测试 MUST 以结构化方式证明并发性（例如，两个任务都必须观察到的顺序），而不是依赖在负载高的机器上容易偶发失败的墙钟时间阈值。

## 理由

**一个世界。** 已废弃的设计维护着两个 Task 宇宙——线程 future 通过库调用连接，协程通过重新编译后的调用连接——外加一个在它们之间摆渡的隐藏循环。这个设计只有一个宇宙，但有两扇门：`run` 从外沿进入，`blocking` 通向边缘。被删除的一切都是模拟成本：`from_async` 及其守护线程循环、`:infinity`（裸 `await` 就是无截止日期的汇合）、生成的 `_gan_try_await` 辅助函数（现在是普通标准库函数）、不可杀死线程的脚注。

**截止时间上的判定，而非异常。** 截止时间是一个预期结果，而非异常结果；`{:error, :timeout}` 可以与 `case` 组合，而 `TimeoutError` 处理会打断流程。其形态效仿 Gleam 的 `try_await`；要求提供超时参数，是鉴于旧的隐式 5000 的实测失败（一个面向模型的表面声称“无截止时间”，背后却有一个隐藏的截止时间）。

**顺序汇合作为产物。** `gather` 被拒绝用于 `all/1`，并非因为行为，而是因为可审阅性：`[await t for t in tasks]` 是 Python 审阅者一眼就能验证的循环，具有相同的有序结果语义，并且不需要通过互操作层进行 splat 传递。

**毫秒**继续沿用：Elixir 肌肉记忆，产物中一处可见的 `/ 1000`。

## 向后兼容性

修订版 1–4 的线程池 Task 仅存在于未发布的工作树中；本修订版将其整体替换。`await/2`、`await_many/2`、`try_await_many/2`、`start/1`、`from_async/1` 和 `yield` 从未发布；它们的替代品是语言的 `await`、`all/1`、`try_all/2`、`async/1`，以及没有对应项（协程本身就是一个值；不存在需要桥接的东西）。

## 安全性与确定性

任务以调用者的信任在调用者的循环上运行任意的 Gandora 代码——不引入新的边界。`blocking/1` 继承 `to_thread` 的默认执行器；该模块自身不保存任何状态。R011 保持套件的确定性。

## 工具与 AI 使用

`Task` 位于上下文包的 std 列表和 MCP 语料库中，其经过验证的整模块示例采用新形态：异步内核（`Task.async` 扇出、`await Task.all` 汇合、带可见截止时间的 `Task.try_await`）位于同步外壳之下，外壳的 `Task.run` doctest 可执行。MCP 服务器本身即是参考消费者：其工具处理程序是 SDK 原生等待的异步函数，其模型调用为 `await Task.try_await(Task.async(agent.run(text)), timeout)` —— 这正是 Python 审查者会手写的产物。

## 一致性

测试 MUST 覆盖：`run` 从边缘返回协程的值；值经 `async`/`await` 往返；按 R011 的结构化并发证明；崩溃在裸 join 处重新抛出，并通过 `try_await` 以 `{:error, e}` 形式到达；任务可观察地取消时的 `{:error, :timeout}`；`all` 的顺序保持；`try_all` 的组截止时间；`async_stream` 的顺序和边界（该边界以结构化方式证明）；每个组合器，包括 `race` 以先到者为准，以及 `recover` 吸收崩溃；`shutdown` 取消；`sleep` 和 `completed` 的往返；以及模块自身的 doctests 在 `gan test` 下通过。

## 变更历史

- 修订版 5，2026-08-07：转向 asyncio。任务成为基于 GEP-0030 修订版 4 原生语法的协程世界之上的库：`run`/`async`/`blocking` 取代线程池，`from_async` 和后台循环被删除，`await/2` 和 `await_many/2` 让位于语言的裸 `await` 和 `all/1`，`try_await` 要求其超时并真正取消，`async_stream` 在信号量下接收可等待对象。线程仅作为 `blocking/1` 保留。
- 修订版 4，2026-08-07：R002 —— `:infinity` 在没有截止时间的情况下等待，两种连接均如此。
- 修订版 3，2026-08-06：与 Gleam 对齐 —— `yield`/`yield_many` 变为 `try_await`/`try_await_many`，返回 `{:ok, v}` / `{:error, :timeout}` / `{:error, e}`；非阻塞组合子 `map`、`tap`、`recover`、`race` 遵循 gleam/javascript/promise。
- 修订版 2，2026-08-06：R011 `from_async` —— 协程成为共享后台循环上的普通任务；协程任务真正取消。
- 修订版 1，2026-08-06：基于 `concurrent.futures` 的初始版本。
