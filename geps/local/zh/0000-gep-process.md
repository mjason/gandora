# GEP-0000: GEP 目的与流程

## 摘要

本提案定义了 Gandora 增强提案（GEP）流程。GEP 在实现之前记录设计决策，向人类评审者和 AI 代理展示稳定的需求，并将已接受的规范与后续的代码、测试、文档和兼容性决策联系起来。

英文 GEP 是规范性来源。同步翻译提供本地化评审，而不会产生多个相互竞争的规范。

## 动机

Gandora 涵盖了一门语言、一个编译器、一个宏展开器、Python 代码生成、与 `uv` 的包集成以及未来的工具协议。非正式讨论不足以保持这些层面的一致性。

需要一个提案系统来：

- 将需求与实现偶然性分离；
- 在代码提交使其代价高昂之前审查破坏性变更；
- 保留决策背后的理由和被拒绝的替代方案；
- 为 AI 智能体提供稳定的标识符和机器可读的元数据；
- 使符合性测试可追溯到规范要求；
- 维护英文和中文视图，避免无声的翻译漂移。

## 范围

若某项变更满足以下任一条件，则需编制 GEP：

- 变更语言语法或可观测的求值语义；
- 新增或修改公开的标准库契约；
- 变更生成代码的约定、工件格式或互操作契约；
- 变更项目配置或依赖解析契约；
- 引入或修改公开的工具链或语义检查协议；
- 创建影响包作者或用户的兼容性承诺。

常规的错误修复（恢复已规范的行为）、内部重构、测试、文档的编辑性修订以及发布自动化工作，无需新设 GEP。

## 术语

- **作者**：负责撰写和修订 GEP 的个人或团体。
- **编辑**：检查流程、元数据、范围和状态的管理者。
- **评审者**：评估技术提案的参与者。
- **规范性文本**：定义一致性的要求。
- **非规范性文本**：理由、示例、历史和实施说明。
- **源 GEP**：`geps/` 目录下的规范性英文文档。
- **翻译**：`geps/local/` 下的本地化、非规范性译本。
- **修订版本**：标识源文本同步状态的单调递增整数，而非 GEP 生命周期状态。

## 规范

### 提案标识与存储

**GEP-0000-R001:** 项目必须使用名称 **Gandora Enhancement Proposal** 及缩写 **GEP** 来指代受本流程管辖的文档。

**GEP-0000-R002:** 规范性源文档必须直接存放在 `geps/` 目录下，并使用文件名格式 `NNNN-short-title.md`，其中 `NNNN` 是零填充的永久提案编号。

**GEP-0000-R003:** 提案发布后，其编号不得被重用，包括在拒绝、撤回或取代之后。提案编号不表示优先级或接受状态。

**GEP-0000-R004:** 下一个提案编号必须从下一个未使用的整数中分配。重命名提案时必须保留其编号。

### 提案类型

**GEP-0000-R005:** 每个 GEP 必须声明以下类型之一：

- **Standards Track**：可观察的语言、标准库、制品、配置、互操作或工具合约；
- **Process**：治理、发布、审查或项目范围的开发规则；
- **Informational**：不定义一致性要求的指导或架构记录。

### 生命周期

**GEP-0000-R006:** 每个 GEP 必须使用以下状态之一：

- **Draft**：正在积极编写，尚未准备好做出决定；
- **Review**：已足够完整以做出决定，除审查编辑外冻结；
- **Accepted**：已批准，作为实现可瞄准的合约；
- **Final**：已接受，并通过一致性证据表明已实现；
- **Active**：已接受的 Process GEP，持续适用；
- **Deferred**：有效的工作被有意推迟；
- **Rejected**：经审查并拒绝；
- **Withdrawn**：由作者在接受前撤回；
- **Superseded**：被另一个已接受的 GEP 取代。

**GEP-0000-R007:** 正常的 Standards Track 演进必须为：

```text
Draft -> Review -> Accepted -> Final
```

被推迟的提案可以返回 Draft。已接受的提案只能通过显式记录的决定（解释兼容性风险）返回 Draft。

**GEP-0000-R008:** 实现不得被视为 Draft 或 Review 提案的真相来源。实验性代码可以为审查提供信息，但只有 Accepted 文本定义目标行为。

**GEP-0000-R009:** Accepted 意味着实现已获授权，而非完成。Final 需要链接到一致性证据和一个已发布的实现。

**GEP-0000-R010:** 一个已接受且持续适用的 Process GEP 应使用 Active 而非 Final。

### 前置元数据

**GEP-0000-R011:** 每个源 GEP 必须以 YAML 前置元数据开头，按此顺序包含以下字段：

```yaml
gep: <integer>
title: <English title>
description: <one-line English description>
author: <name or names>
status: <lifecycle status>
type: <proposal type>
areas:
  - <area>
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
revision: <positive integer>
requires: [<GEP numbers>]
replaces: [<GEP numbers>]
superseded-by: <GEP number or null>
resolution: <decision URL or null>
translations:
  <language>: <relative path>
```

**GEP-0000-R012:** 日期必须使用 ISO 8601 日历格式。元数据中的 GEP 引用必须使用整数提案编号。空关系必须使用空数组，不存在的单个关系必须使用 `null`。

**GEP-0000-R013:** 当英文源在首次审查发布后发生变更（包括编辑性变更）时，`revision` 必须递增。修订号不得减少或重用。

**GEP-0000-R014:** 未知的元数据字段必须使用 `x-` 前缀，直到本流程 GEP 将其标准化。消费者必须保留未知的 `x-` 字段，且不得从中推断规范性含义。

### 必需的文档结构

**GEP-0000-R015:** Standards Track GEP 必须按此顺序使用以下顶层章节：

1. Abstract
2. Motivation
3. Scope
4. Terminology
5. Specification
6. Rationale
7. Backwards Compatibility
8. Security and Determinism
9. Tooling and AI Usage
10. Rejected Alternatives
11. Open Questions
12. Conformance
13. Change History

Process 和 Informational GEP 可省略不适用的章节，但必须保留 Abstract、Motivation、Specification 和 Change History。

**GEP-0000-R016:** Standards Track 或 Process GEP 中的规范性要求必须具有形式为 `GEP-NNNN-RMMM` 的稳定标识符。标识符在 Review 开始后不得重新编号。已删除的要求仍保留。

**GEP-0000-R017:** 要求陈述必须使用 MUST、MUST NOT、SHOULD、SHOULD NOT 或 MAY 等关键词，且仅当它们以大写形式出现时，才具有 RFC 2119 和 RFC 8174 定义的含义。

**GEP-0000-R018:** 示例仅在精确语法或输出是合约的一部分时才被标记为规范性。否则，示例是解释性的，不得覆盖要求文本。

**GEP-0000-R019:** 在提案进入 Accepted 之前，必须解决或明确推迟开放问题。已接受的 GEP 不得使一致性依赖于未解决的问题。

### 规范与实现

**GEP-0000-R020:** 规范性文本必须定义可观察的行为、不变量、接口、失败行为、兼容性边界和一致性。它不得要求内部文件布局、算法、Rust 类型或 Python 辅助程序，除非该细节本身是公共兼容性合约。

**GEP-0000-R021:** 实现讨论必须放在明确标记为非规范性章节或单独的实现文档中。实现说明不得静默地添加要求。

**GEP-0000-R022:** 提案可在实现之前定义迁移和验收标准，但必须以可观察的结果来描述它们。

### 翻译政策

**GEP-0000-R023:** 英文源 GEP 是规范性的。翻译必须声明其非规范性，并必须链接回英文源。

**GEP-0000-R024:** 翻译必须存放在 `geps/local/<language>/NNNN-short-title.md`。初始简体中文翻译目录为 `geps/local/zh/`；其元数据语言值为 `zh-CN`。

**GEP-0000-R025:** 源 GEP 必须先编写，然后才能进行翻译。在英文源具有修订号后，可在同一变更中准备 Draft 翻译。

**GEP-0000-R026:** 翻译必须复制提案编号、状态、类型、创建日期、更新日期和源修订号。它必须添加：

```yaml
language: <locale>
source: <relative path to English GEP>
source-revision: <English revision translated>
translation-status: Current | Stale
```

**GEP-0000-R027:** 只有当 `source-revision` 等于英文的 `revision`，并且所有规范性和实质性非规范性章节都已翻译时，翻译才为 Current。否则，必须标记为 Stale。

**GEP-0000-R028:** 在进入 Review、Accepted 或 Final 之前，Standards Track 提案必须有一个 Current 的 `zh-CN` 翻译。此要求只能通过修订本流程 GEP 来更改。

对于 `zh-CN` 以外的语言环境，可提供翻译，但任何状态转换均不要求。

**GEP-0000-R029:** 不改变英文含义的翻译修正会更新翻译的 `updated` 日期，但不会更改英文修订号。如果翻译暴露了源文的歧义，则必须首先修复英文源并递增其修订号。

**GEP-0000-R030:** 机器翻译可产生翻译的初始草稿。机器生成的翻译必须在将其 `translation-status` 设置为 Current 之前由人工审核，并且要求标识符、代码块和前置元数据值必须与源文逐字节相同，但翻译元数据要求更改的字段除外。

### AI 可读的编写规则

**GEP-0000-R031:** 每个 GEP 必须从其自身的元数据、术语、要求和显式依赖关系中可理解。它应避免依赖对话历史或未陈述的仓库知识。

**GEP-0000-R032:** 具有 Gandora 特定含义的术语必须定义一次并一致使用。规范性文本应优先使用显式名词，而不是模糊的代词，如“它”、“这个”或“系统”。

**GEP-0000-R033:** 当引用的陈述是规范性时，跨文档引用必须使用稳定的 GEP 和需求标识符。

**GEP-0000-R034:** 一致性证据应将测试、诊断、公共符号和发布说明映射回需求标识符。AI 生成的实现计划必须引用其打算满足的需求。

**GEP-0000-R035:** GEP 前置元数据和需求标识符是结构化接口。自动化可对它们进行索引，但生成的索引必须对照源 GEP 进行检查，且不得成为第二个真相来源。

### 审查与接受

**GEP-0000-R036:** 从 Draft 移动到 Review 需要完整的元数据、必需的章节、稳定的需求标识符、已解决的内部矛盾以及一个 Current 的中文翻译。

**GEP-0000-R037:** 审查必须评估语义、兼容性、确定性、失败行为、工具影响、包影响和一致性标准。仅凭代码风格或实现便利性不足以构成理由。

**GEP-0000-R038:** 接受必须在前置元数据中记录一个持久的决议 URL 或仓库决策引用。接受的修订必须不可变；后续的规范性更改需要修订号，并且在兼容性更改时，需要一个新的 GEP 或显式的重新开放决定。

**GEP-0000-R039:** Final 状态需要一致性证据、已发布的制品版本、当前所需的翻译，以及没有未解决的规范性 TODO。

### 仓库索引与清单

**GEP-0000-R040:** `geps/README.md` 必须列出每个源 GEP，包括编号、标题、类型、状态、修订号和可用的翻译。

**GEP-0000-R041:** 该索引是导航辅助工具。如果与源前置元数据冲突，则源前置元数据优先，并且必须修正索引。

**GEP-0000-R042:** 仓库必须提供 `geps/geps.jsonc` 作为机器可读的文档清单。清单必须声明其模式版本、规范性源语言环境、已知的翻译语言环境以及 GEP 源路径。它必须使用允许注释和尾随逗号的 JSON，并且消费者必须将其解析为数据，而不执行内容。

**GEP-0000-R043:** 清单不得重复提案状态、修订号、标题、要求或其他权威性前置元数据。这些值必须从引用的源 GEP 中读取。如果清单路径与 GEP 不一致，则源 GEP 优先，并且必须修正清单。

## 理由

稳定的需求标识符使得设计、实现、测试、诊断以及AI生成的工作计划能够引用同一意图单元。单调递增的源修订版本比提交哈希更简单，可用于检测陈旧翻译，并在提案提交之前发挥作用。

选择英语作为规范来源，是因为包生态系统、协议标准和外部贡献者通常使用英语规范。要求在审查之前提供最新的中文翻译，可以保留项目的主要审查工作流，而不会创建两个规范文本。

明确允许机器辅助翻译，因为项目使用LLM翻译脚本；要求在翻译被标记为Current之前经过人工审核，能够将质量责任落实到人，而不是模型。

Accepted和Final是分开的，因为批准必须在实施之前。这可以防止现有代码被当作意外的规范。

此流程为年轻仓库刻意保持精简：嵌入式文档快照和发布渠道在当前未纳入范围，直到对应的Standards Track GEP对其作出定义。

## Backwards Compatibility

GEP-0000 引入了一个新流程，对语言运行时兼容性没有影响。

## 安全与确定性

GEP 文档是数据，且 MUST NOT 包含可执行元数据。索引 YAML 前置元数据的工具必须使用安全的解析器，且不得从标签中实例化特定于语言的对象。

外部文本、生成的摘要和翻译不能授予接受或改变规范性含义。状态变更需要仓库审查和持久的决议记录。

## 工具与AI使用

AI 代理应按以下顺序阅读 GEP：

1. 读取源文件的元数据与依赖项；
2. 阅读术语与规范；
3. 将工作映射到需求标识符；
4. 使用基本原理与已拒绝的方案以避免重新打开已确定的决策；
5. 在提议实现之前检查未解决问题与状态；
6. 仅当翻译其源修订版本为当前时方可使用。

AI 代理 MUST NOT 推断草案文本已授权实现。在接到实现 GEP 的请求时，代理应在改变公开行为之前报告其状态与未解决问题。

## 被拒绝的替代方案

### 将所有设计保留在一个语言设计文档中

一份大型文档使得独立决策难以审查、版本控制、被取代或映射到测试。它作为概览仍有价值，但不应作为唯一的决策记录。

### 将翻译版本设为规范版本

两种规范语言会不可避免地产生冲突解决的歧义。同步的非规范翻译模型在保留单一权威的同时提供了可访问性。

### 使用文件名或标题而不携带元数据

仅含散文的文档对于工具和 AI 代理来说难以可靠地索引。YAML 前置元数据在 Markdown 保持人类可读的同时提供了小型结构化契约。

### 要求接受前必须有实现

这会颠倒期望的工作流程，并使实现细节决定规范。实验性原型可能存在，但评估的是契约。

## 开放问题

无。

## 一致性

GEP 仓库符合本提案的条件是：

- 每个 GEP 都包含有效的必需前置元数据；
- 编号和需求标识符是唯一且永久的；
- README 索引与源前置元数据匹配；
- 处于“审查”或更后阶段的 Standards Track GEP 需有当前的中文翻译；
- 翻译需声明并与源版本匹配；
- 状态转换和接受决议需满足本流程。
