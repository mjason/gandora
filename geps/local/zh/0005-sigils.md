# GEP-0005: 符号标记

## 摘要

Sigil 是 Elixir 的 `~name<delimiter>body<delimiter>` 字面量家族。本提案为 v0 层面增加了四个 sigil：`~w`（单词列表）、`~s`（自由选择分隔符的字符串）、`~r`（编译后的正则表达式）和 `~python`——一个原始 sigil，它将逐字的 Python 表达式拼接到生成的代码中。`~python` 是这样的逃生口：当宿主语言已经可以直接表达某些内容时，它使编译器保持小巧。

## 动机

单词列表和正则表达式是常见的字面量，其纯字符串拼写很嘈杂（`["a", "b", "c"]`、模式中的转义反斜杠）。更重要的是，一种编译到 Python 的语言需要一个有原则的转义方式：当一个 Python 表达式没有 Gandora 拼写方式（例如推导式、`yield`、特殊运算符）时，作者应当逐字嵌入那个表达式，而不是将其封装在 Python 辅助模块中。带语言标签的嵌入体干净地解决了这一问题，Gandora 以 Elixir 的符号语法呈现。

## 范围

上述四个符号、它们的定界符集合以及它们的原始/插值划分。用户自定义符号、符号修饰符（`~r/x/i`）、带类型的 `extern` 句柄、基于文件的嵌入以及附加符号（`~D` 日期、`~U` 时间戳）被推迟。

## 术语

- **符号**：字面量 `~name` 后跟一个分隔的正文。
- **插值符号**：小写名称的符号，其正文支持 `#{...}` 插值。
- **原始符号**：大写名称的符号，其正文按原样处理。

## 规范

**GEP-0005-R001：** 符咒（sigil）由 `~` 后紧跟一个字母名称和一个定界主体构成。支持的定界符对包括 `( )`、`[ ]`、`{ }`，以及对称的 `/ /`、`" "`、`| |`，外加三引号 `""" """`。括号类定界符可嵌套；对称定界符不可嵌套。

**GEP-0005-R002：** 在每个符咒主体中，反斜杠原样传递，但反斜杠可以对闭合定界符进行转义（且 `\\` 表示闭合定界符前的字面反斜杠）。插值型符咒额外支持 `#{expr}`；原始型符咒将 `#{` 视为文本。

**GEP-0005-R003：** 紧跟在闭合定界符后的字母（Elixir 符咒修饰符）必须产生诊断信息，说明不支持修饰符。

**GEP-0005-R004：** `~w(one two three)` 求值为空格分隔的单词列表 `["one", "two", "three"]`。当启用插值时，将在运行时对插值后的字符串进行分割。

**GEP-0005-R005：** `~s(...)` 求值为一个字符串，等同于双引号字符串，但具有定界符的自由度。

**GEP-0005-R006：** `~r(...)` 求值为一个编译后的正则表达式：它编译为 `re.compile(<body>)`，并隐式包含 `import re`。主体逐字节（依据 R002）传递至 Python 的 `re` 引擎，因此约定使用 Python 正则表达式语法，而非 Erlang 的。

**GEP-0005-R007：** `~python(...)` 是一个原始符咒，其主体必须是单个 Python 表达式；编译器将其原样拼接（用括号包裹）到生成代码中该符咒的表达式位置。编译器仅验证主体非空，不执行其他验证；错误由 Python 抛出。在符咒位置作用域内的 Gandora 绑定，在主体中按 GEP-0001-R015 的名称映射可见。

**GEP-0005-R008：** `~python` 主体对编译器不透明：宏卫生性不会重命名其中的名称，工具必须将其按 Python 而非 Gandora 处理。在 v0 中，宏展开不得生成 `~python` 主体。

**GEP-0005-R009：** 未知的符咒名称必须产生诊断信息，说明该符咒名称及支持的符咒集合。

## 原理说明

原始/插值大小的区分完全遵循 Elixir 的惯例，因此知识可迁移。反斜杠直通（而非完整的转义处理）使得 `~r(\d+)` 无需双重转义即可书写，这与 Elixir 处理 sigil 主体的方式一致。

`~python` 有意编译为带括号的逐字拼接，而非 `eval` 或辅助函数调用：输出保持可读性、零运行时开销，且行为完全等同于手写的 Python 代码。宿主语言是特性，而非故障模式——此处限制为单个表达式，以确保拼接不会破坏周围语句结构。语句级嵌入（函数、类）仍由普通 Python 模块及 `pyimport` 负责。

## 向后兼容性

纯新增；`~` 此前是无效字符。

## 安全性与确定性

Sigils 是字面量；编译过程不执行代码。`~python` 将作者编写的文本拼接到生成的输出中，就像手写的 Python 文件包含它一样——它不赋予项目自身 Python 文件所缺乏的任何能力。生成的输出仍然是确定性的。

## Tooling and AI Usage

Agents 应当优先使用 `~w`/`~r` 而非手动构建的等价形式，仅当 Python 表达式没有对应的 Gandora 拼写时才使用 `~python`，并且保持 `~python` 体为单一可读表达式——任何更长的内容都应归属于通过 `pyimport` 导入的 Python 模块。

## 被拒绝的备选方案

### 将 `~r` 编译为 Gandora 端的正则表达式 AST

便携的正则表达式模型可以将表面语法与 Python 解耦，但目标平台是 Python，其 `re` 模块无论如何都是运行时；重新编码正则表达式语法毫无收益，并且会破坏从 Python 复制粘贴的便利性。

### 语句级别的 `embed python do ... end` 块形式

语句级别的嵌入会重复 `pyimport` 普通 Python 模块已经做得很好的功能，并且会诱使在模块作用域内进行非结构化的代码注入。仅限表达式的 sigil 保持了逃逸出口的最小化。

### 在 sigil 主体中完全处理 Elixir 转义

在 `~r` 内部处理 `\n` 等转义序列会迫使正则表达式作者对每个反斜杠进行双重转义——这是经典的 sigil 失败案例；透传行为与 Elixir 的实际行为以及正则表达式用户的预期相符。

## 开放问题

本修订版无。

## 一致性

测试 MUST 覆盖：每个分隔符对，包括嵌套和转义后的闭合分隔符；在 `~w`/`~s`/`~r` 中的插值，以及在 `~python` 中无插值；单词拆分（字面量和运行时）；保留反斜杠的 `re.compile` 输出；在表达式位置中的 `~python` 拼接，包括在管道和调用内部；修饰符诊断（R003）；以及未知魔法符号诊断（R009）。
